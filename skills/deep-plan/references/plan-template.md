# Plan Document Template

Copy this structure into the plan output path (e.g. `docs/PLAN.md`). Every
section is required, in this order. Replace the guidance text; keep the
headings. Tag claims `VERIFIED` / `UNVERIFIED` / `CORRECTED` as defined in
SKILL.md. Write for a reader who has never seen the planning conversation —
a goldfish will be exactly that reader.

## Contents (the 10 required plan sections)

1. Context — intent, definition of done, Research Question list
2. Findings: current state — inventory table (works/half-wired/dead)
3. Findings: framework ground truth — vendor/versioned-doc facts
4. Audit findings — defects, worst-first, each with file:line
5. Corrections — beliefs proven wrong, plus goldfish corrections
6. Gap analysis — numbered, classified BROKEN/MISSING/FIGHTS-THE-FRAMEWORK
7. Design decisions — one committed decision per gap, reversibility-tagged
8. Roadmap — milestones M0…, dependency-ordered, skeleton-first, spikes
9. Risk register — pre-mortem-generated, no generic entries
10. Verification — copy-paste automated commands + manual E2E checklist

```markdown
# Plan: <task title>

> Generated by deep-plan on <date>. Ground-truth source: <vendor path or docs URL + version>.
> Goldfish: NOT RUN | PASSED (G1 r1, G2 r2, G3 r1) | OPEN ITEMS (<n>, see §5)

## 1. Context

Why this work exists, in at most 5 lines: the system, the intent, the
definition of done, and the explicit non-goals. Then the final **Research
Question list** — one line per question with its answer (evidence-cited) or
its `UNVERIFIED` tag. No question is silently dropped.

## 2. Findings: current state

| Component | Status | Evidence |
|-----------|--------|----------|
| `src/Checkout/CartCalculator.php` | works | wired in `config/services.xml:41` |
| `admin settings "discount cap"` | half-wired | collected in `ui/Settings.vue:88`, never read |
| `src/Legacy/PriceHelper.php` | dead | no references outside itself |

## 3. Findings: framework ground truth

| Mechanism | Fact | Source |
|-----------|------|--------|
| Rule engine | `RuleInterface::match()` receives `RuleScope` | `vendor/…/Rule/RuleInterface.php:18` |
| Event | `checkout.cart.processed` fires after collectors | docs v6.7 <URL> |

Include mechanisms that turned out NOT to exist — those are findings too.

## 4. Audit findings

- **[SEVERITY] Short title** — what is wrong, why it matters, `file:line`.
  Order: security > data loss > correctness > reliability > maintainability.

## 5. Corrections

Beliefs that turned out wrong, with the evidence that corrected them
(`CORRECTED: <old belief> → <new fact> (file:line)`). Mandatory content; if
empty, state why the research still qualifies as adversarial.

Goldfish findings go here too, kept apart from the above:

- `CORRECTED (goldfish): <gap in the plan itself, now fixed>`
- `REJECTED (goldfish): <issue> — <one-line reason>`
- Open items still unresolved after 2 rounds, listed as `OPEN (goldfish)`.

## 6. Gap analysis

Numbered. Each gap: classification (BROKEN / MISSING / FIGHTS-THE-FRAMEWORK),
one-line description, evidence links to sections 2–4.

## 7. Design decisions

### Decision <N>: <title>
- **Options considered:** A (one line), B (one line)
- **Decision:** the ONE committed choice
- **Reversibility:** REVERSIBLE / ONE-WAY — ONE-WAY additionally marked
  user-confirmed or `UNCONFIRMED`
- **Rationale:** complexity / architecture fit / framework blessing, citing section 3
- **Rejected because:** one line per rejected option

## 8. Roadmap

Milestones, dependency-ordered ("Phase" is reserved for deep-plan's own
protocol). M0 is always shippable security/correctness fixes. If the plan
builds new functionality, M1 is a **walking skeleton**. Every `UNVERIFIED`
appears as a named **spike task**, first in the milestone that depends on it.
For EACH milestone:

### M<N>: <name>  (effort: S/M/L)
- **Objective:** one line
- **Depends on:** M<K> / nothing
- **Entry criteria:** what must be true to start
- **Tasks:**
  - [ ] `M<N>-T1` — action naming the exact files/classes/migrations it touches
  - [ ] `M<N>-T2` — …
- **Exit criteria:** a runnable command and its expected result, or an
  explicit manual step with its observable outcome — never "works well"

## 9. Risk register

Pre-mortem: assume the plan failed three months from now and write the top
causes. No generic entries that fit any plan.

| Risk | Likelihood | Impact | Mitigation / rollback |
|------|-----------|--------|----------------------|
| Migration locks table on prod-size data | medium | high | run on replica first; batched migration |

## 10. Verification

**Automated** — exact copy-paste-runnable commands and what output means pass:

    bin/phpunit --filter CartCalculatorTest
    npm run typecheck

**Manual E2E** — numbered steps a human can follow, each with the expected
observable result.
```

---

## Quality bar for this document

- An implementer opens it and never needs to ask which file, what change, or
  how to verify.
- A reviewer can spot-check any claim by following its citation.
- A stakeholder reads sections 1, 8, and 9 and understands scope, order, and risk.
- Implementers tick tasks but never rewrite or delete them; a deviation
  changes the plan first.
