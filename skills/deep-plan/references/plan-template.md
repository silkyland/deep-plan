# Plan document template

Copy the structure below to the plan output path. Keep the eleven headings
and their order (deep-plan-ingest reads them); replace the guidance under
each with real content. Example rows show the shape only.

Paths in the plan are relative to the project root, which section 1
names.

````markdown
# Plan: <task title>

> Generated by deep-plan on <date>. Ground-truth source: <vendor path, or docs URL + version, or "none available">.
> Goldfish: NOT RUN

## 1. Context

At most 5 lines: the system and its project root, the intent, the
definition of done, the non-goals. Then:

- **Research Questions**: one line each, with its answer and citation, or
  its `UNVERIFIED` tag. Every question from Phase 0 appears.
- **Assumptions**: each `assumed (framing default)`, each ONE-WAY
  decision still `UNCONFIRMED`, and whether the Decision Brief was
  confirmed. Write "none" if there are none.
- **Open questions**: what only the owner can answer. Write "none" if
  there are none.

## 2. Findings: current state

| Component | Status | Evidence | Tag |
|-----------|--------|----------|-----|
| `src/Checkout/CartCalculator.php` | works | wired in `config/services.xml:41` | VERIFIED |
| admin setting "discount cap" | half-wired | collected in `ui/Settings.vue:88`, never read | VERIFIED |
| `src/Legacy/PriceHelper.php` | dead | no references outside itself | VERIFIED |

**Data flow**: the write path and the read path through the code in scope,
one line each, with citations.

## 3. Findings: framework ground truth

| Mechanism | Fact | Source | Tag |
|-----------|------|--------|-----|
| Rule engine | `RuleInterface::match()` receives `RuleScope` | `vendor/…/Rule/RuleInterface.php:18` | VERIFIED |
| Event | `checkout.cart.processed` fires after collectors | docs v6.7 <URL> | VERIFIED |
| Queue driver | supports delayed jobs | not installed locally; docs unreachable | UNVERIFIED |

Include mechanisms you expected that turned out not to exist in this
version.

## 4. Audit findings

- **[severity] Short title**: what is wrong, why it matters, `file:line`,
  and whether it is in scope for this plan.

Worst first: security, data loss, correctness, reliability,
maintainability. Write "none found" plus what was checked if the audit was
clean.

## 5. Corrections

- CORRECTED: <old belief> → <new fact> (`file:line`)

Write "none" plus what was checked if no belief turned out wrong.

Findings from the goldfish gates are listed separately, because they are
gaps in this document rather than wrong beliefs about the code:

- CORRECTED (goldfish): <gap in the plan, now fixed>
- REJECTED (goldfish): <issue> — <one-line reason>
- OPEN (goldfish): <issue that needs the user's decision>

## 6. Gap analysis

Numbered. For each gap: its class (BROKEN / MISSING /
FIGHTS-THE-FRAMEWORK), the concrete mismatch in one line, and the evidence
in sections 2–4.

## 7. Design decisions

### Decision <N>: <title> (closes gap <numbers>)
- **Decision:** the one committed choice
- **Reversibility:** REVERSIBLE, or ONE-WAY (user-confirmed / `UNCONFIRMED`)
- **Rationale:** complexity, architecture fit, framework support, citing section 3
- **Rejected:** one line per alternative considered, or "no real alternative"

## 8. Roadmap

Milestones `M0`, `M1`, … in dependency order. They are called milestones
because "phase" already means a deep-plan phase. Ordering rules:

- Security and correctness defects from section 4 that are in scope are
  fixed in the first milestone, so that it can ship on its own before any
  feature work.
- New functionality starts with a walking skeleton: the thinnest slice that
  runs end to end, rather than one finished layer at a time.
- Each `UNVERIFIED` claim a milestone depends on becomes a named spike
  task, placed first in that milestone, stating what to check and what to
  do for each outcome.
- A small change can be a single milestone. Do not split it to have two.

### M<N>: <name> (effort: S / M / L)
- **Objective:** one line
- **Depends on:** M<K>, or nothing
- **Entry criteria:** what must be true to start
- **Tasks:**
  - [ ] `M<N>-T1`: the action, naming the exact files, classes, or migrations it touches
  - [ ] `M<N>-T2`: …
- **Exit criteria:** a command and its expected output, or a manual step
  and what the person should observe

## 9. Risk register

Imagine the plan was carried out and failed three months later; list the
most likely causes. Each entry should be specific to this plan. A risk
that would fit any project ("requirements may change") does not help the
implementer.

| Risk | Likelihood | Impact | Mitigation and rollback |
|------|------------|--------|-------------------------|
| Migration locks the orders table at production size | medium | high | batched migration; rehearse on a replica; rollback script in M2-T4 |

## 10. Verification

**Project commands**: the build, test, and lint commands the repo already
has, as found in its manifest or CI config (or "none exist").

**Automated**: the exact commands to run and what output means pass.

    bin/phpunit --filter CartCalculatorTest
    npm run typecheck

**Manual**: numbered steps a person can follow, each with the expected
observable result.

## 11. Change log

Starts empty: "No changes since acceptance." Anyone who implements this
plan follows these rules:

- A detail inside a task is yours to decide.
- A choice the plan does not cover, or a decision the code contradicts: if
  it is reversible and within this plan's scope, decide it after checking
  the evidence and log it here first. Otherwise stop work on the affected
  tasks and ask the owner.
- Append entries (`### R<N>: <title> (<date>)` with trigger, evidence,
  change, decision); never edit or delete one. Update sections 1–10 to
  match, and mark obsolete tasks `dropped (R<N>)`.
````

Phase 7 replaces the `Goldfish:` header line; the allowed forms are listed
under "Finishing" in [gates.md](gates.md).

During implementation, tasks are ticked off but not rewritten or deleted.
A deviation is recorded by changing the plan first.
